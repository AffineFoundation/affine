## What this checkout turns on

1. **One seat per coldkey.** The chain reader fills `Registration.coldkey` from `SubtensorModule.Owner`. The first sync after start may write many `refreshed` coldkeys once.
2. **Leave the back when a file is valid.** Before a round picks seats, demoted waiting seats with a valid file get a `seats_restored` journal record and rejoin the normal zone. No charge.
3. **Cutover idle guard** and the documented double-turn UIDs 893 / 876 / 981 (docs only for the UIDs; the guard matters only on a future import).
4. **Terms** in the publisher text (file / submission / batch / round / king / tasks / rollouts / looks).

### 1. Ask for a stop after the round (no hard kill)

`9d6be0fd` already supports the stop file. In a second shell with `SN120_WORK_DIR` set:

```
touch "$SN120_WORK_DIR/logs/run-loop.stop-after-round"
F="${SN120_WORK_DIR:?}/logs/run-loop.stop-after-round"; if [ -e "$F" ]; then echo "a stop is asked for since $(date -u -r "$F" +%Y-%m-%dT%H:%M:%SZ)"; else echo "no stop is asked for"; fi
```

What happens:

- If a round is open (`r000011`), `run` finishes that round, then the next `run` sees the file, opens no new round, prints a line that starts with `stop after the round: obeyed.`, and exits 0. The loop removes the file and stops. Look for `STOPPED after the round, as asked` in `run.log`.
- If no round is open, the current or next `run` obeys at once.

Do **not** `systemctl stop` while a round trains, unless you accept the cost table in "A checkout only" in CUTOVER.md.

Confirm the loop is down:


### `seats_restored` (hard rule)

`seats_restored` is a new journal kind from PR 233.

- If **no** `seats_restored` record exists yet: safe to roll back to `9d6be0fd`.
- If a `seats_restored` record **was already written**: do **not** check out a build that lacks that handler. Old code refuses the journal (`JournalCorrupt` / unknown kind). Stay on this combined commit (or any later build that knows `SEATS_RESTORED`). Rolling the code back past that record breaks journal load on every host that reads it (GPU box and AffineValidator weights/links).

Coldkeys already written into later `registrations_synced` / `refreshed` entries stay on those seats when the journal replays. That alone does not block a rollback to `9d6be0fd`; the `seats_restored` kind does.

### What rollback does **not** need

- No `set-params`
- No journal rewrite
- No change to `params_hash` / `code_digest` (they match `9d6be0fd` on both commits)
