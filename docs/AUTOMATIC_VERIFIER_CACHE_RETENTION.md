# Automatic verifier cache lifecycle

This extends the forensic recovery documented in VERIFIER_CACHE_LIFECYCLE.md. The implementation and service drafts require root review; preparing these files does not install a timer, restart a worker or authorize deletion.

`ops.automatic_verifier_cache_lifecycle` is an operator-only oneshot. Observation is the default. It checks the actual controller PID/ticks/argv/source and private config/scope bindings, scans only explicit role scopes and approved known alias pairs, and protects actual worker CLI cache mappings. GPU work and scientific CPU preparation defer retirement. At most one obsolete physical cache or one exact two-alias cluster can retire per cycle after complete authority-signed canonical R2 checkpoint readback, fresh queue/dispatch/current/pending guards and node-local full hashes/reference checks. Canonical R2 objects, source archives, logs, jobs and reports are never deleted.

The apply policy pins the config, scopes, controller observation, output/quarantine directory, operator and node helpers, optional reference ledger and optional alias catalog. Journal creation uses private canonical parents, O_EXCL/O_NOFOLLOW, file mode600, file fsync and directory fsync. A per-role pending record precedes the remote operation. Timeout, refusal or uncertainty writes an fsynced uncertainty record and leaves that role quarantined from further deletions; the next oneshot can still observe other roles. No automatic reset/retry exists. Node cluster operations separately retain start/completion/uncertainty journals, including failures between the two renames.

## Retiring a historical reference rather than a protection set

The legacy protection policy retains failed/expired queue references until their retirement is authenticated. Historical records remain durable; they do not require obsolete cache replicas to be kept forever. `ops.verifier_cache_reference_retirement` accepts only authority-signed, named reference entries whose original request exhausted the exact retry policy and whose signed expiry passed. It authenticates the original terminal replacement decision, unchanged job/manifest/source/runtime/frozen hashes, the complete replacement worker report signature/token/digest, and exact canonical R2 original/replacement job/report documents. New, queued or leased requests immediately protect their checkpoint, regardless of prior entries. Current/pending checkpoints, active manifests, unfinished dispatches, pending authenticated training outputs and actual worker mappings are independent protections.

In the historical CP660 preparation, four E7 original failed attempt3 requests were the remaining unfinished references. Four original authority-signed replacement decisions and complete worker reports were verified independently, including16 canonical R2 history documents. Four unsigned entries are prepared for root review/signing. They neither mutate the queue nor authorize checkpoint deletion. CP093 was the current checkpoint at that historical boundary and had actual E9 references. Fresh current/in-flight guards govern every later cycle.

`ops.verifier_obsolete_alias_cluster` handles only an obsolete cluster with exactly two explicitly catalogued ordinary canonical directories. Every approved file must have matching device/inode/size and exactly two links, exact complete membership and full SHA equality to its signed archive. Unknown third links, symlink roots, active references or changed metadata refuse. Its physical reclaim estimate counts the inode cluster once; actual post-operation free bytes are recorded. It cannot retire a current/pending/mapped checkpoint. The actual CP660 pair was traced to original hydration/recovery receipts and its metadata rechecked; deletion still requires fresh full hashes, R2 readback, signed reference entries, explicit root policy and an idle window.

## Future role cache maps and capacity

The `--prepare-future-maps` mode streams authority-signed R2 checkpoints and hashes explicit same-host cache candidates. Select current/pending checkpoints explicitly with `--map-checkpoint` where necessary. It emits separate future-only maps and CLI arguments; it never edits the live config or worker. Missing/incomplete/corrupt caches are not admitted merely because their directories exist.

Capacity admission uses fresh free bytes from the actual worker workspace filesystem, complete streamed sizes for missing checkpoints, the configured signed artifact policy's compressed maximum and an explicit2GiB operational reserve. It refuses insufficient capacity before hydration or worker admission. `future_worker_arguments` requires complete admitted maps, replaces stale cache flags and preserves every other original argument, including identity seed path, authority, coordinator and workspace. Root must separately approve a future boundary handover and actual new process evidence. A running worker's static map does not automatically grow as training produces checkpoints.

The prospective service should run the bounded lifecycle on normal-completion cadence (for example OnUnitInactiveSec120), without `--prepare-future-maps` in every timer invocation. Prepare maps at reviewed worker/source transitions. Keep a single approved output directory so pending quarantine cannot be bypassed by a new output path. Changing the controller binding, helper bytes or scope requires a new pinned policy. Unknown training layouts or missing authentication fail closed; they are not grounds to weaken the science contract.

Local controls include real temporary hardlink clusters, second-rename uncertainty, FD/cwd/mmap references, real Ed25519 job/decision/report/ledger signatures, R2 document tampering, new/leased request re-protection, fsynced private journals and transport-quarantine repeat refusal. These are lifecycle controls, not numerical or learning-quality qualification.

## Root-activated verifier-2 scope

On 2026-10-05 the root operator activated a separately signed policy bound to the actual V13 controller process, source and configuration. The timer uses `OnUnitInactiveSec=120` and permits one verified retirement per cycle. Its two approved roots contain the current verifier backend checkpoints and one complete historical CP5756 attempt cache. Initial observations found complete obsolete CP28 and CP5756 replicas, while CP6a was current and protected. Both obsolete checkpoints had complete authenticated ten-file R2 readbacks before activation; each retirement still performs its own fresh archive and node checks. No historical queue entries, workers, GPU scientific jobs or bucket objects are removed.

The policy retains a single private output/quarantine directory. Future checkpoint changes update the dynamically protected set; current weights and all actual in-flight input checkpoints remain protected. A changed controller process, source/configuration, helper or scope requires a newly reviewed exact policy, rather than silently reusing an old process binding. Actual retirement and free-space results belong in the private cycle completion evidence; activation alone is not a deletion claim.
