# Prospective CPU selection peer

This default-off operator bridge supports confirmed-blacklist training selection while retaining an already qualified scientific bundle. It does not change forward computation, sampling, probabilities, TOPLOC, native grading, optimizer math, learning rate or quotas. Publishing this implementation does not activate training exclusion or authorize a remote peer.

The ordinary scientific source and its original 177-module inventory remain separate from the coordinator and remote CPU operator. The reviewed metadata profile is stored under `operator_profiles/confirmed_blacklist_cpu_selection_v1/subnet/`. Its four files are preserved byte for byte from the CPU-qualified profile. They are an explicit operator override, not a claim that the frozen scientific archive contains new code. This profile supports the committed-unaudited, small-commitment-v2 scientific context; it does not qualify a future token-only or different numerical contract.

## Exact signed bindings

The coordinator freezes the latest authenticated assessment once per new opening under an approved automatic-selection authorization. Active confirmed-policy blacklist identities are excluded from training selection. New, unaudited, UNKNOWN, numerical and infrastructure outcomes remain eligible. Audit and reward inventories are preserved.

The manifest retains the signed policy, protected round and selected snapshot in its enriched computation binding. A separate authority-signed peer grant pins:

- the original scientific source and complete 177-module map;
- exactly four CPU metadata modules;
- a minimum future round and epoch prefix;
- the separate peer entry and durable runner hashes;
- explicit execution authorization.

Each original job gets a signed peer admission only after persistent transport fields are finalized. The admission binds the complete original payload minus its own circular envelope, full manifest, enriched computation binding, protected round, selection snapshot and selected receipt inventory. The ordinary job signature covers all fields including that admission. Reports bind the full original job hash. Saved retries use the original job and snapshot; they do not reissue a new admission or resample selection.

`committed_training_inputs.validate_job` requires the peer admission when the scientific map does not contain the new selection helper. It does not project away policy or round fields to satisfy an old parser.

## Remote execution identity

`ops/learner_selection_cpu_peer.py` defaults to CPU admission only. Explicit backend execution requires a separately signed true grant. The frozen backend normally reloads its own metadata modules, so preflight alone is insufficient. The admitted entry explicitly routes `subnet.backend_jobs.FreshSourceFinder` to the four pinned CPU modules while retaining the original source routes for everything else. The execution receipt declares that override and its separate identity. Original on-disk scientific hashes remain genuine; those hashes are not represented as the executed CPU override bytes.

`ops/learner_selection_cpu_peer_runner.py` defaults to review-only. It requires pinned entry/runner bytes, isolated `-I -B -X pycache_prefix=...` with a never-existing prefix, an original checkpoint lease and exclusive launch marker. It records actual child PID/start ticks and `wait()` exit status. Failure or an uncertain launch preserves the marker; observation timeout never triggers a duplicate job.

The durable learner admission also authenticates a separately recorded remote CPU readiness document. Its exact trainer endpoint, interpreter, source path, metadata paths, hashes and authorization digest must match the signed config. Coordinator and peer parser bytes must agree. A profile cannot silently authorize mining, evaluation or verifier overrides. The scalar audit-policy-v3 parser is pinned separately; frozen scientific audit code is not replaced.

## Singleton future handoff

A continuously opening learner can use an optional signed `stop_after_current_round` guard. It binds the exact current published opening, epoch and parent. Under the existing singleton it resumes that original round with `run(config, once=True)` and stops naturally before another opening. An unpublished opening, passed round or different epoch refuses. The stop receipt is not a substitute for authenticating the signed scientific closure.

Use a bounded CPU drain unit with `Restart=no`; preserve all remote scientific actors, original jobs, manifests, state, queue, history and optimizer lineage. Admit the new CPU overlay and native execution-root authorization separately. Activate selection only in a genuinely new opening after the current original round closes. The implementation does not change an already saved opening.

## CPU controls

Portable tests cover full signed job/manifest bindings, round/parent/source/inventory changes, signature and helper tampering, post-admission transport changes, saved retries, real isolated runner refusals, the backend's actual metadata reload and coordinator dispatch construction. They use test-only signing keys and synthetic metadata, not production jobs or claims of numerical qualification.

The optional frozen-dependency route uses the public relative-path/hash fixture for the original f213 177-module inventory:

```sh
AFFINE_CPU_PEER_FROZEN_SOURCE=/owned/admitted/frozen/source \
  python -I -B -X pycache_prefix=/owned/new-unused-prefix \
  tests/test_learner_selection_operator_bridge.py
```

That root must already be admitted and retained; tests do not download models, read signing seeds or access the network. A CPU test pass does not authorize deployment or establish scientific performance.
