`subnet/gpu_runtime.py` is an isolated runtime pilot, not a live controller backend. It loads an approved full checkpoint into CUDA BF16 with eager attention, sm86, TF32 disabled, deterministic algorithms and `CUBLAS_WORKSPACE_CONFIG=:4096:8`. TOPLOC bit extraction uses two native threads. The verifier retains exact TOPLOC comparison and the existing full-probability tolerance; it does not permit CPU/GPU replay interchange.

The runtime uses the generic environment/session and harness rendering/action/observation interfaces. Its isolated sampling implementation places token tensors and RNG on CUDA and supports autoregressive, public candidate, visible-copy candidate and per-turn policies. It produces the same complete trajectory/probability/proof format as the CPU runtime. Live integration should replace the duplicated rollout/sampling loops with small device hooks: Runtime constructor/device/dtype/profile, tensor allocation and generator device in harness sampling, CPU conversion at proof/probability serialization, and a versioned approved backend factory selected by the authenticated manifest. Verifier workers must require the identical signed backend profile and checkpoint file map.

The retained 1.7B training pilot uses an explicitly partial-parameter objective: a reference-relative preference update of the output head with frozen decoder features. The head is tied to the input embedding in this model, so the saved checkpoint changes that shared parameter too. It uses AdamW at1e-3 for one step, checks an actual parameter change and writes a complete normal model/tokenizer checkpoint. This is memory-bounded real optimization, not full-model finetuning or an assertion of autonomous task improvement. A production trainer must select and version its optimizer/objective separately.

`ops/new_subnet_gpu_training_pilot.py` searches the original Oolong test16k task215 using public Counter+0 and Counter+1 commands. It independently reloads approved weights to audit the honest positive/negative trajectories before optimization, then saves the full new checkpoint on the retained pod, reloads its exact new file map and independently audits a fresh rollout. Original temporal-label tasks216/217 are separate free-autoregressive heldouts, evaluated without the task215 Counter policy before and after. Operator reports/artifacts live under `state/multi-environment/gpu-training-pilot/`; large checkpoint bytes remain only on the retained pod. The report, rather than this design note, records actual completion and outcomes.

Full network deployment still requires signed GPU profile/checkpoint publication, remote miner/verifier/trainer routing, the reviewed resource contract and private grader transport. This pilot does not write blockchain weights, change the live CPU runtime, rent another node or authorize a hardware-tolerance relaxation.
