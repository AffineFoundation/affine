# Prospective statistical rewards

`continuous-statistical-reward-activation-v1` is a separate operator-signed
activation for netuid120, the owner, activation ID, effective time, approved
source hashes, one million integer units per raw point, and floor after hourly
aggregation. It does not activate chain writes by itself.

Configure `continuous_reward_activation_document` only for new epochs. The
controller binds `continuous_reward_contract` before its first signed manifest,
using actual epoch registration snapshots. Strict `live_reward_contract` and
this statistical contract are mutually exclusive. Historical nonpayable epochs
cannot be promoted. Remote opening publishes the final quota-bearing manifest
and immutable first-opening/registration sidecars. Completion publishes signed
actual learner completion only after durable checkpoint/state commitment.

`continuous_reward_bridge.project` authenticates the original signed hourly
aggregate, per-epoch snapshots, complete audit-cohort populations, first opening
attestations, registered identities, and actual learner completions. The bridge
recomputes the hourly aggregate and converts its raw penalized statistical points
to integer units. A changed UID/public key denies the whole hour; the owner is
excluded. Completion must be inside the actual UTC hourly interval. Missing
prospective contracts and incomplete provenance refuse publication.

The bridge trusts authenticated operator score snapshots generated by the
continuous audit service. It does not re-execute inference or claim that all
training pairs have been audited. Population commitments and explicit eligible
IDs remain bound separately from audit observations. The produced
`continuous-statistical-hour-units-v1` is incompatible with the old strict reward
proposal. A separate submit API requires the same fresh single-writer process
receipt for execution; ChainAdapter then rechecks chain ownership, identities,
rate limits and duplicate windows. Root must hold the existing global writer
lock, suppress prior writers and sign the projected proposal before handoff.
This patch does not enable a live writer or execute a chain transaction.

## Separate training precision

A prospective FP32 generation manifest may declare `training_runtime` with
version `separate-bf16-persistent-training-runtime-v1`, exact
`cuda-bf16-eager-sm90-v1` backend and numerical profiles. This is accepted only
with the committed unaudited learner and persistent optimizer policy. Miner,
verifier and evaluator retain the signed FP32 generation profile; training
loads BF16 parameters with the existing FP32 CPU masters/moments/objective.
Job source hashes and the signed manifest bind both profiles. Reports state
actual execution revision, generation revision and training-runtime digest.
The training computation binding includes the override. Historical manifests
without this field keep their original execution profiles.
